What is slowing G-HUIM down, from the host to the warp

The GPU is not waiting on data transfer and it is not short of bandwidth: no unit passes 60% of its peak and DRAM never passes 30%. It is waiting on latency. In the kernels that dominate the run, 60–90% of warp stall cycles are spent waiting for a global load to come back, because each lane walks its own transaction through 8-byte entries, so only 14% of every 32-byte sector fetched is used. Your layout suspicion is right about the cause, but the limit is load latency, not bandwidth.

Findings

Measured

While mining, the GPU is busy 99–99% of the time between the first and last kernel. Host syncs and readbacks cost 1.5–2 ms per run. The GPU is not starved by the CPU.

Measured

Inside the kernels, speed of light is low everywhere: SM throughput 8–38%, issue slots 13–49%, L2 up to 60%, DRAM up to 30% (602 GB/s). Nothing is saturated, so the kernels are latency-bound.

Measured

Level 1 to 3 hold 66% of BFS static kernel time. There, 81% of stall cycles are global-load waits, Nsight reports 71–78% of requested L2 sectors as excess from uncoalesced access, and global atomics move 1.1 G sectors (35 GB) through L2 in one launch.

Measured

Late levels are a different problem: 65–67% of stall cycles are __syncthreads barriers, because hundreds of thousands of tiny tasks each run a 256-thread block through several synchronised passes.

The profiles use the base clock (1.11 GHz, --clock-control base) and flush caches between replays, so absolute times in this section are about 1.4× the nsys times. Ratios and percentages are unaffected. Each kernel family was sampled on 2–3 launches chosen to cover its large launches.

The layout question

  • Access pattern, confirmed. Every pass has each lane take one transaction (i = i0 + lanes.rank) and walk its entries e[k+1+d] alone. A warp-wide load therefore touches up to 32 different transactions. At BFS static level 1 Nsight reports only 4.6 of 32 bytes per sector used by loads (6.8 for stores), and 71–78% of the L2 sectors the big launches request as excess from uncoalesced access (41% in the late levels).
  • Dependent loads, confirmed. Each kept entry costs two chained global loads: the entry, then rename[entry.item] in scratch. That chain is 46% of the stall samples in huge_merge (child.cuh:131) and 10–19% in scan_subtree (passes.cuh:82).
  • Contended global atomics, confirmed. add(p.local[item], …) and add(p.subtree[z], …) issue one 64-bit atomic per entry into arrays of only ~100 items. BFS static level 2 sends 1.1 G atomic sectors to L2 (35 GB) in 52 ms, and L2 is the busiest unit there at 54%.
  • Repeated work, confirmed. Four passes each re-read the parent entries, and each re-runs the binary search. Level 2 pushes 180 GB through L1 to move 24 GB from DRAM.
  • Bandwidth, ruled out. DRAM never exceeds 30% of peak and the largest launches use 0.2–0.6 TB/s of 2.04 TB/s. A better layout would raise useful bytes per sector rather than reduce total bytes.
  • Host transfer, ruled out. The only host-to-device copy is the 88 MiB root database (4 ms).

What to change, in order of evidence

These are proposals from the measurements above. None is implemented, and the estimates are not promises.

1 · Largest, least risky

Compute each transaction's extension-item position once

find_item plus same_kept_items are about 20% + 16–28% of stall samples in every kernel. Pass 1 already finds the position k for every transaction. Store it in the per-task scratch (4 bytes per transaction, which the scratch layout already budgets for) and have passes 2, 3a, 3b and the duplicate check read it.

2 · Large

Keep the per-item tables in shared memory

local[], subtree[] and rename[] are indexed by item and hold 100 or fewer items at the first levels (fewer deeper). Accumulate with shared-memory atomics and flush once per block, and read rename[] from shared memory. That removes the global atomic traffic (35 GB through L2 in one launch) and one of the two dependent loads per entry. Fall back to the current path for tasks with too many items.

3 · Medium, more work

Make entry scans coalesced

Split Entry into separate item and utility arrays. Passes that only test rename[item] then read 4 bytes per entry instead of 8, and utilities are read only for kept entries. For the large-task kernels also let a warp scan one transaction with lanes on consecutive entries, instead of one transaction per lane.

4 · Late levels

Stop using a 256-thread block for tiny tasks

Barriers are 65–67% of stall cycles at late levels. Adaptive already routes small tasks to warp and sub-warp kernels. For the static method, the sweep below shows 256 to 512 threads is the best fixed size, so static has no better setting to fall back on.

5 · DFS only

Replace the single-block selector

select_kernel is one block of 1,024 threads. It costs 22 ms of 318 ms of adaptive kernel time at 8M, with barriers about 30% of its stalls. The sampled launches were its first, smallest batches, so its large-batch behaviour is only known from nsys timing.

Static block size sweep (kernel time at minutil 8M)

Static work is a fixed block per task, so block size is its only knob. Small blocks lose because the lane-per-transaction scans need many lanes in flight to hide load latency. 1,024 loses to barrier and occupancy costs. Adaptive beats the best static size by 1.4× (BFS) and 1.7× (DFS).

How this was measured, and gaps

  • The code is built with -O3 -lineinfo, so Nsight Compute can attribute stall samples to source lines in optimized code, including lines inside inlined device functions. cmake -DGHUIM_PROFILE=ON also prints registers, spills and shared memory per kernel at compile time. -G is not used, because it disables optimization and would profile different code.
  • ncu ran 13 targeted jobs through profiling/run_ncu.sh as root (GPU counters are restricted for normal users). Three of the DFS adaptive jobs (block, warp, sub-warp) matched no kernel because of a regex, and the BFS adaptive warp job caught only tiny launches. The script is fixed, and these are the missing data points. DFS adaptive shares its kernels' structure with BFS adaptive, and its huge-task kernels match BFS's within 5% on every metric.
  • Late-level and sub-warp numbers come from one or two launches each, so they show the regime, not a precise average.
  • Per-function shares are stall-sample shares, not elapsed-time shares, and they are rounded.
