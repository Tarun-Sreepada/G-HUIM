Where the time goes in G-HUIM, and what is still unmeasured

The GPU is not starved by the host while it mines: it is busy 99–99% of the time between the first and last kernel. Most of a run is spent before that, in CUDA startup, file loading and database build. Whether the kernels themselves stall on memory could not be measured, because GPU performance counters are blocked on this machine.

Findings

Measured

Between kernels the GPU is almost never idle: 94–188 gaps per run at minutil 8M, 1.5–2.1 ms in total. At 6M the DFS runs lose under 3 ms and the BFS runs about 26 ms (still under 8% of kernel span), from the extra scratch chunks of the large middle levels.

Measured

At minutil 8M a run takes about 0.9 s, of which only 17–24% has the GPU busy. About 0.3–0.4 s is CUDA context creation (a bare cudaFree(0) takes 300–420 ms here), 0.15 s is loading the dataset and 0.05 s builds the root database on the CPU.

Measured

Inside the kernel span, early levels dominate. In BFS the first three levels hold 66% (static) and 57% (adaptive) of kernel time, with only 106 to 6,201 tasks. Launches under 50% fill take 35–41% of summed kernel time.

Not measured

Stall reasons, cache hit rates, coalescing and DRAM throughput. ncu fails with ERR_NVGPUCTRPERM, and nsys GPU metrics are blocked the same way. The data-layout hypothesis therefore stays unproven. The next section lists what the available numbers do and do not say about it.

The GPU is busy while it mines

Idle gaps are the stretches inside the first-to-last-kernel span where no kernel ran on any stream. Launch fill is the share of resident-block slots one launch can occupy at once, from its grid size and the kernel's theoretical occupancy, averaged by kernel time. A value of 100% means a full wave or more. It says how much of the GPU a launch could use, not how efficiently the warps run.

Adaptive configs have a summed kernel time well above their GPU busy time because bins run on parallel streams. Static configs run one kernel at a time, so for them the two are equal.

Early levels carry the kernel time

The same search, level by level, in BFS at minutil 8M. Level 1 has 106 tasks, each a large database, so a static launch is 106 blocks of 256 threads on 114 SMs: about 15% of the resident-block slots, for 70–80 ms. Adaptive slices those tasks over many blocks and finishes level 1 in 28 ms. From level 7 on, the levels hold hundreds of thousands of small tasks and take 5 ms or less.

What the numbers say about data layout

  • Writes are not the limit. Level 1 writes 432 MiB of child databases in 28.5 ms (adaptive), about 16 GB/s against 2,040 GB/s peak. The same pattern holds on the next levels.
  • Re-reading the parent is plausible but unverified. The root database is 87.9 MiB (the H2D copy), larger than the 50 MB L2. Level 1 has 106 tasks that each scan it, so one pass is at least 9.1 GB of reads. In 28.5 ms that is 327 GB/s per pass (16% of peak), and in 80 ms (static) 114 GB/s. Each task makes several passes, which would put the adaptive level 1 well above that. Pass counts and cache behaviour need counters.
  • Register-limited occupancy. The task kernels use 31–63 registers per thread and the block, warp and sub-warp kernels are capped at 50–78% theoretical occupancy, by registers. None of the top kernels uses local memory.
  • The DFS selector. DFS select_kernel is a single block of 1024 threads, 22 ms in total at 8M (7–10% of its kernel time), so it runs one block while the rest of the GPU waits.

None of this proves memory stalls. The distinguishing counters are long-scoreboard stalls, sectors per request, L1 and L2 hit rates and DRAM throughput. They are collected by profiling/run_ncu.sh, once counter access is enabled.

To finish the memory and compute analysis

Hardware counters need administrator action on this server. Either run the prepared script once as root, or lift the restriction in the driver (this needs a driver reload, so nobody else may be using the GPUs):

sudo bash profiling/run_ncu.sh # 13 targeted runs, one GPU, each under timeout # or, to allow every user: echo 'options nvidia NVreg_RestrictProfilingToAdminUsers=0' | sudo tee /etc/modprobe.d/nvidia-prof.conf # then reload the nvidia kernel modules or reboot, and run the script without sudo

The script profiles the heaviest launches of every kernel family at minutil 8M, with the speed-of-light, memory-workload, warp-state, occupancy and source-counter sections plus raw metrics for coalescing, cache hit rates, atomics and DRAM bytes. It uses -c and -s to limit each run to a few launches. Its metric names were checked against this GPU's metric list, but the script itself has not run, since counters are blocked.

Commands used for the nsys data

nsys profile --trace=cuda,nvtx,osrt --cuda-memory-usage=true --sample=none -o <cfg>_<minutil> \ build/G-HUIM --input accidents_utility_spmf.txt --minutil <M> --search <bfs|dfs> --method <static|adaptive> --total-memory 8G python3 profiling/analyze.py # sqlite exports to profiling/data/nsys_summary.json
